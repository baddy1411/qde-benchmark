# Containerised reproduction environment

## Status: built, tested, and portability measured

Built on 2026-08-06 for `linux/arm64`. Base image pinned by digest
(`sha256:a02e9c54…`), lockfile exported (55 packages), `environment_id`
`4f86489394a5`.

**The full unit-test suite passes inside the image: 110 passed, 2 skipped.**

`make docker-verify --scope classical` regenerated the 19 artifacts of the
classical cross-system battery and diffed them against their committed
counterparts (`container_verification.json`).

### Result: conclusions portable, low-order digits are not

Reproduction is **not** bit-identical across BLAS implementations. Every
decision-level outcome is nonetheless preserved:

| Check | Result |
|---|---|
| Leaderboard ordering | unchanged, 3 of 3 systems |
| Selected NG-RC configuration | unchanged, 3 of 3 systems |
| Pairwise DM decisions at p<0.05 | 0 flips in 270 pairs |
| Sign of the effect | 0 flips in 270 pairs |
| Model Confidence Set membership | byte-identical, 3 of 3 |

### Why Hénon is different: the generator is not reproducible

The two flow systems agree to `8.7e-9` (Lorenz-63) and `9.1e-10` (Mackey–Glass)
as a maximum disagreement in any single predicted value, on series scaled to
[0,1]. Their generated trajectories are bit-identical in both environments.

Hénon does not agree at all — **every** model differs by ~0.98, which is the
scale of the signal. That uniformity is the clue: it is not the solve, it is the
input. The Hénon generator, an iterated map, produces:

| step | host vs container |
|---|---|
| 0–49 | bit-identical |
| 50 | first difference, 4 ulp (`-0.55621878968540472` vs `...517`) |
| 101 | exceeds 1e-6 |
| 134 | exceeds 0.5 |
| last 1000 | correlation r = 0.03 — uncorrelated |

That is textbook Lyapunov amplification of a last-place rounding difference, most
likely FMA contraction differing between the two toolchains. It is a property of
iterating a chaotic map in floating point, not a pipeline defect — and the flows
reproduce exactly because their integrators compile to identical operations here.

**Consequence:** bit-identical regeneration of Hénon results requires the
original environment. Elsewhere its absolute numbers differ while its orderings,
selected configurations and statistical verdicts do not — exactly what the
decision-level table above measures.

Two files reported SHAPE_DIFFERS (`lorenz_climate.csv`, `mackeyglass_climate.csv`,
7 rows vs 4). Not a defect: those committed files are a union of two runners —
`experiments/cross_system.py` writes the classical rows and `experiments/quantum_cross.py` merges the
`qrc_*` rows in afterwards. A classical-only regeneration correctly produces 4.

### A measurement caveat worth repeating

The first run of this verification reported "27 IDENTICAL" over a whole
directory. 24 of those files were never regenerated by the scope being run, so
they were identical only because nothing had touched them. The scope now lists
the exact files its runner writes. The same run also reported a maximum relative
difference of 6.8e+279, which was a metric artifact: the column was `nrmse_std`
for a deterministic model, where both values are ~1e-23. Relative differences are
now computed only where the committed magnitude exceeds 1e-12, with absolute
differences reported otherwise.

## What the first container run found

Running the suite with the host repository bind-mounted produced one failure,
`test_cli.py::test_cache_flag_is_transparent`, asserting `0.5485 != 1.0385`.

It was **not** a cache defect, and it was **not** BLAS drift. The bind mount
carried the host's 1.6 GB `feature_store` into the container, so the cached path
read host-computed feature matrices while the uncached path computed new ones
under OpenBLAS. With no mount, all three paths agree byte-for-byte and the suite
is green.

That contamination exposed a genuine latent bug, now fixed. The test believed
`FeatureStore()` roots at `cwd/feature_store` and called `monkeypatch.chdir()`
accordingly, but `feature_store._default_root()` resolves to
`repo_root/feature_store`. The test had therefore always read and written the
*real* repository cache rather than an isolated one. On a single machine that is
invisible, because the warm cache holds exactly the bytes the test would have
computed. It is only visible when the two environments disagree in the last bits.
The test now redirects `_default_root` itself.

The underlying amplifier is worth stating plainly: at this test's configuration
(300 points, `alpha=1e-6`) the quantum feature matrix has rank 12 of 16 and
`cond(XᵀX) ≈ 10²¹`. A rank-deficient system with almost no regularisation turns
last-bit input differences into percent-level output differences. That is
consistent with the ill-conditioning the thesis already reports for the quantum
feature matrices, and it is the reason artifact-level agreement has to be
*measured* rather than assumed.

## Why this exists

Chapter 8 reports byte-identical regeneration of every committed artifact, but
only on one machine: an Apple-silicon laptop where NumPy links against Apple's
Accelerate framework. §10.5 declares cross-platform floating-point behaviour
untested. That is a real gap, and a container is the standard way to close it.

The image pins the interpreter, the full package closure, and the BLAS binary.
That splits the reproducibility claim into two claims that deserve different
words:

| Claim | What it means | Status |
|---|---|---|
| **Repeatability** | same environment, same bits | shown, on one machine |
| **Portability** | different BLAS / architecture, same bits | **untested** — this is what `docker-verify` measures |

## What to expect from the verification

**Probably not byte-identity, and that is not a defect.** Accelerate and OpenBLAS
reduce floating-point sums in different orders. On a chaotic system those
differences amplify. The honest outcome is a measured bound — "agreement to
within a relative difference of *x* on the reported columns" — not a claim of
bit-identity across platforms.

If the numbers come out further apart than the thesis's declared tolerance
(relative 1e-9, accepted only for BLAS-level reduction noise in a listed set of
derived columns), the correct response is to report that, not to widen the
tolerance until it passes.

BLAS thread counts are pinned to 1 in the image, because threaded BLAS reduces in
a non-deterministic order. That makes runs *inside* the image repeatable, at the
cost of speed.

## Usage

```bash
make docker-build     # build the image
make docker-lock      # export the resolved closure to requirements.lock.txt
make docker-pin       # print the FROM line to pin the base by digest
make docker-env       # print the environment fingerprint inside the image
make docker-test      # run the unit-test suite inside the image
make docker-verify    # regenerate a scope and diff against committed artifacts
```

`docker-verify` stages `git archive HEAD` into a scratch tree and gives the
container *that* tree, read-write. The committed repository is never mounted, so
a container run cannot overwrite evidence. This mirrors the isolated-worktree
pattern used for the full re-execution in Chapter 8.

Scopes: `--scope smoke` (one ESN, ~1 min) and `--scope classical` (the
cross-system battery, ~10–20 min). The quantum families are deliberately not
offered: they are slow, and BLAS drift is characterised just as well on the
classical path.

## `environment_id`

Appendix E defines `environment_id` as a hash of the pinned dependency lockfile
and declares it non-nullable. Nothing computed it — it was passed as `None`
everywhere, so every registry row violated that part of the contract.

`qdepipe/envid.py` now computes it as `sha256(requirements.lock.txt)[:12]`,
returning `None` when nothing is pinned rather than hashing whatever happens to
be installed. `environment_fingerprint()` additionally records the interpreter,
platform, machine, BLAS name and thread pinning — the parts of an environment a
lockfile cannot capture, and the usual reason two correctly-pinned runs still
disagree in the final digits.

## Build risks that only a build will settle

- `torch==2.8.0` resolves to `2.8.0+cpu` from the PyTorch CPU index. cp39 wheels
  for `manylinux_2_28_aarch64` and `x86_64` were confirmed to exist, so this
  should work on Apple silicon natively and on amd64.
- `lightgbm` and `xgboost` need `libgomp1`, which the image installs. If either
  fails at import, that is the first thing to check.
- Python 3.9 is end-of-life. It is used here because it is what produced the
  committed artifacts; changing it would change the thing being verified.
